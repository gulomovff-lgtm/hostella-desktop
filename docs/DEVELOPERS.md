# Hostella — карта проекта для разработчика

Документ отвечает на вопрос «куда смотреть и куда класть». Продуктовое описание
(что умеет система) — в [HOSTELLA_OVERVIEW.md](HOSTELLA_OVERVIEW.md).

## С чего начать

```bash
npm install
npm run dev      # Vite + Electron (кассовое приложение)
npm test         # чистая логика, node --test, без сети и Firebase
npm run build    # веб-сборка
```

Для входа нужен доступ к боевому Firestore: пароли проверяет Cloud Function,
локальной заглушки нет. **Не логиньтесь чужим пользователем в браузере** — живая
сессия рассылает реальные Telegram-уведомления и может автостартовать смену.
Для проверки интерфейса делайте временную смоук-страницу с мок-пропсами
(`smoke-X.html` + `smoke-X.jsx` в корне, vite отдаёт их по `/smoke-X.html`) и
удаляйте её сразу после.

## Куда что класть

| Каталог | Что там | Правило |
|---|---|---|
| `src/utils/` | Чистые функции: расчёты, форматирование, правила | Без React и без Firestore. **Здесь пишутся тесты** |
| `src/hooks/use*Actions.js` | Запись в Firestore: гости, смены, расходы, клиенты | Единственное место, где приложение меняет данные |
| `src/hooks/use*.js` | Фоновая автоматика и подписки | Возвращает только то, что нужно разметке |
| `src/components/Views/` | Экраны | Крупный экран — папка: `Вид/shared.js` + части |
| `src/components/Modals/` | Модальные окна | |
| `electron/` | Главный процесс, IPC, автоматика портала e-mehmon | Рендерер обращается только через `preload.js` |
| `functions/` | Cloud Functions: вход, Telegram, брони, бэкап | Секреты только здесь, в клиент не попадают |

## Как течут данные

```
Firestore ──▶ useAppData ──▶ App.jsx ──▶ экраны (пропсы)
                                │
                                └──▶ use*Actions ──▶ запись в Firestore
```

`App.jsx` — сборочный узел: состояние экрана, фильтр филиала, роутинг вкладок и
разметка. Фоновая автоматика вынесена в хуки и подключается одной строкой:

| Хук | За что отвечает |
|---|---|
| `useAppData` | Подписки на все коллекции |
| `useAutoCheckout` | Авто-выселение просроченных (пять гейтов защиты) |
| `useEmehmonAutomation` | Госпортал: отметки, вывод, сверка, суммы |
| `useSystemHealth` | Версия клиента, перехват ошибок JS и сбоев Electron |
| `useOfflineQueue` | Операции, накопленные без сети |
| `useAutoClientSync` | Плановое пополнение базы клиентов |

## Договорённости, которые не выводятся из кода

Каждая написана после реального бага — менять их можно, но осознанно.

- **Филиал.** Гость без `hostelId` считается `hostel1`. Сравнивать филиалы нужно
  через нормализацию: `(g.hostelId || 'hostel1') === hostelId`.
- **Какой филиал «текущий».** Берётся ВЫБРАННЫЙ в фильтре, а не привязка
  пользователя (`filterByHostel` и `emehmonHostelId` следуют одному правилу).
  Иначе кассир, смотрящий чужой хостел, видит одни данные, а пишет в другие.
- **Опознание кассира.** По `staffId` **и** `staffLogin`: document ID пользователя
  меняется при пересоздании записи, логин — нет.
- **Смена.** Сутки 9:00 → 9:00. Передача смены делит сутки и зарплату 50/50
  (`shareRatio`), вся касса и поступления переходят принявшему — он сдаёт один
  общий отчёт (`utils/shiftReport`, `utils/shiftMath`).
- **Сутки в e-mehmon.** Считаются формулой самого портала:
  `round(часы / 24 + 0.35)`, минимум 1. Ровно 24 часа — это ещё одни сутки.
  Своя формула округления разошлась бы с колонкой «Срок проживания» в портале
  (`utils/emehmonAmount`).
- **Сессии e-mehmon.** У каждого филиала своя: состояние портала хранится по
  хостелам, занятость тоже — сверка одного не должна блокировать другой.
- **Протухшие записи.** Задача перестаёт быть задачей через 30 дней
  (`utils/staleness`) — иначе счётчики копят историю за все годы.
- **Деньги договора.** Всё, что меняет сальдо договора без движения денег —
  перенос сальдо между договорами и списание долга — оформляется позицией в
  `extraCharges`, а НЕ платёжной записью: иначе фиктивные деньги попадут в кассу
  и в отчёт смены. Списание помечено `writeOff: true`, доступно только админу и
  вырезано из `extraCharges`, которые возвращает `computeContractFinancials`, —
  поэтому ни один отчёт его отдельной строкой не покажет, оно молча уменьшает
  «Начислено». Формула в `utils/contractFinancials.js` и в `detailedGroups`
  (ManualStayView) должна совпадать — иначе карточка и попап аренды разойдутся.

- **Пароли.** Проверяются Cloud Function `authenticateUser`, хеши (PBKDF2) лежат
  в закрытой коллекции `userSecrets`. Поле `users.pass` пока сохраняется для
  старых сборок касс — удалить после перехода всех на 0.13+.

## Ловушки

- **Порядок в App.jsx.** Внутри `useEffect` можно ссылаться на функцию, объявленную
  ниже, а как аргумент хука — нельзя: она вычисляется сразу и падает с
  `ReferenceError`. Вызывайте хук ниже места объявления зависимости.
- **Сборка не ловит опечатки в именах.** `vite build` пройдёт, а экран упадёт в
  браузере. После любой перестановки кода откройте страницу и посмотрите консоль.
- **Главный процесс Electron не перезагружается на лету.** Правки в `electron/`
  видны только после перезапуска приложения.
- **Деплой после `npm run dist`.** В `dist/` остаётся electron-сборка с
  относительными путями. Веб публикуется **только** через `npm run deploy` —
  голый `firebase deploy` сломает вложенные маршруты сайта.
- **Черновик релиза.** `electron-builder` создаёт релиз со статусом Draft, а
  авто-апдейтер черновики игнорирует: после `npm run dist` обязательно
  `gh release edit vX.Y.Z --draft=false`.

## Линтер

```bash
npm run lint        # проверить
npm run lint:fix    # починить то, что чинится само
```

Настроен на **реальные ошибки**, а не на стиль (`eslint.config.js`):

- **Ошибки** — то, что ломает приложение: необъявленные имена (`no-undef`),
  дубли ключей, нарушения правил хуков, невидимые неразрывные пробелы вне строк.
  Их должно быть ноль.
- **Предупреждения** — неиспользуемые переменные и зависимости эффектов
  (`exhaustive-deps`). Часть нарушается осознанно: таймеры читают данные через
  refs, чтобы не пересоздаваться. Смотреть стоит, чинить — по ситуации.
- **Выключено** — правила React-компилятора из `eslint-plugin-react-hooks` v7
  (`static-components`, `purity`, `set-state-in-effect` и другие). Они рассчитаны
  на код, переписанный под компилятор, и на этой базе дают сотни ложных
  срабатываний.

Линтер видит то, чего не видит сборка: `vite build` спокойно соберёт файл с
обращением к несуществующей переменной, а линтер это назовёт.

## Как добавить экран

1. Компонент в `src/components/Views/`. Если сразу видно, что он вырастет за
   ~600 строк — заводите папку и `shared.js` с расчётами.
2. Расчёты — в `src/utils/` отдельным модулем и с тестом в `tests/`.
3. Запись данных — через существующий `use*Actions` или новый по тому же образцу.
4. Пункт меню — в `src/components/Layout/Navigation.jsx` и `MobileNavigation.jsx`
   (там же права доступа: `permKey`, `adminOnly`).

## Выпуск

Порядок и ловушки описаны в разделе «Ловушки» выше; кратко:
`npm test` → `npm run build` → поднять версию в `package.json` → коммит →
`firebase deploy --only functions,firestore` (если менялся сервер) →
`npm run dist` → опубликовать черновик релиза → `npm run deploy`.
